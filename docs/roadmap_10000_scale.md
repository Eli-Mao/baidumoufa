## 规模实验顺序

依次执行 100、500、1000、3000、5000、10000 目标。每个规模必须记录输入数据版本、随机种子、窗口生成参数、算法版本、运行时间、峰值内存、CSV/JSON 输出、物理复核和约束报告；通过验收后才进入下一规模。

每个规模比较 V1、V2、V3 和 V4，并报告实际任务数、覆盖目标数、覆盖率、总分、30 秒切换违规、48 小时冷却违规、物理复核失败数、运行时间和峰值内存。

## V4 范围

V4 在现有调度接口上实现全局收益优先、时间平移、时长优化、任务替换、站点重新分配、未覆盖目标插入、冲突修复、局部搜索和大邻域搜索。10000 目标时使用候选剪枝、分块和高效索引。所有候选解必须通过统一约束检查器后才可计分。

## 当前阻塞条件

1. GitHub 分支只包含项目骨架，没有可用于规模实验的原始轨道和站点数据。
2. 本机 `Task4_Phase0_DataCheck/data/raw/orbits.tle` 当前只有 29 颗卫星，TLE 历元集中在 2026-08-02/03，而规划期是 2026-10-01 至 2026-10-07；不满足“10000 目标真实合法轨道数据”条件。
3. 项目文档仍记录 UTC/北京时区和轨道文件格式待最终确认；在确认前不能生成可提交的规模结果。
4. 现有 `Task4_Phase0_DataCheck` 测试入口存在包导入路径错误；这不是 50 目标修复证据的问题，暂不修改原项目。

## 启动门槛

收到与规划期匹配、可追溯来源的至少 10000 颗轨道数据，以及最终时间基准和轨道格式确认后，先在独立副本完成 100 目标 smoke/regression，再自动推进后续规模。原项目目录保持只读，实验结果写入独立工作副本和带规模/版本号的目录。
