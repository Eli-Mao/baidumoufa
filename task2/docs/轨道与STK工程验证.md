## 1. 太阳同步设计与 J2 传播

新生成构型默认使用 `stk` 约定。生成、合法性检查、传播和评估通过同一模型入口选择约定，并在输出中记录 `rate_model`。历史 `first_order` 输入仍可明确识别和复现；混合两种约定的输入会被拒绝。旧评分参考文件没有模型标记时按 `first_order` 处理，不能与新 `stk` 构型直接混算。原优化器的区域指标仍是历史格点代理，太阳同步速率统一不代表其评分几何已经升级。

赛题高度定义保持 `a = 6371 + h`，单位 km；仿真为圆轨道，输入为 J2000 平均根数，历元为 2027-01-01 00:00:00 UTC，时长 7 天。太阳同步目标节点进动率为 `360/365.2422` 度/天。STK 约定在节点和近地点速率中使用含 J2 修正的平均运动，与倾角反解使用同一组速率公式。

令 `p=a(1−e²)`、`n=√(μ/a³)`、`K=J2(Re/p)²`，共享实现采用：

```text
n_bar = n × [1 + 3/4 × K × √(1−e²) × (3cos²i−1)]
Ω_dot = −3/2 × K × n_bar × cos i
ω_dot =  3/4 × K × n_bar × (5cos²i−1)
M_dot = n_bar
```

速率单位为 rad/s；用 `Ω_dot = 2π/(365.2422×86400)` 求逆行倾角。历史 `first_order` 在前两个速率中使用 `n`，因此不能把它的倾角反解与新约定的传播器混用。J2 描述地球扁率造成的长期轨道面进动；太阳同步利用这一进动率跟随太阳平均运动，保持近似恒定的地方太阳时，而不是靠每圈主动调整轨道面。

重力常数来自本机 STK 的 Gravity Model 数据提供器和安装数据：`μ = 398600.4415 km³/s²`，J2 参考半径 `6378.1363 km`，`J2 = 0.0010826264877881395`。原始读数见 [native_gravity.json](../out/model_alignment/native_gravity.json)。这些数值没有通过拟合 Python/STK 轨迹误差取得；也没有用重力文件中的未归一化系数替代实际运行时读数。

STK J2 在 ICRF 中传播。对新设计，先解出 ICRF 中的太阳同步倾角，再转换为交付所需的 J2000 平均根数；因此 J2000 倾角会随轨道面的升交点赤经产生很小的变化。`sso.design_inclination()` 是生成和检查共用的入口，不能简单给所有轨道面填同一个 ICRF 倾角。

独立实机检查覆盖 500、600、700 km，以及每个高度的 0°、90°、180°、270° 四个轨道面，共 12 组。使用与提交文件相同的六位小数输出，再由 STK 原生传播测量七天节点进动率；最大误差约 `6.52×10⁻⁸ 度/天`，小于项目选定的 `10⁻⁶ 度/天` 门限。原始 28 星属于历史倾角约定，本次只重算其传播与访问，没有修改其倾角。

## 2. 独立几何与 STK 对齐

正式工程验证使用以下模型：

- 地面点采用 WGS84 大地纬度和椭球坐标；保持赛题规定的轨道高度换算方式。
- 使用冻结 EOP、UT1、极移以及 ERFA 的 IAU 2006/2000A 变换处理 ICRF 到地固系。STK 11.6 的 J2000/FK5 输出另外按其未修正的 IAU 1976/1980 约定处理，避免错误叠加 dPsi/dEps。
- 相机采用地心对地指向、地固速度定向，两轴半视场角均为 0.81°。定向所用的速度遵循 STK 的开普勒轨道速度约定；含长期项导数的诊断速度另行处理。
- 全球按明确的 1° 格心点表逐点计算。10 s 和 5 s 是保守候选搜索间距，访问端点由事件求根得到，不是把这些时刻的命中值当作完整访问窗口。
- 长三角采用原资料包中的三个正式外环，直接判断矩形视场与连续区域的交集，不用区域格点命中代替整体访问。按卫星统计访问，计入首尾间隔。

几何计算不读取 STK 星历或访问结果来生成自身答案；STK 输出只用于事后核对。轨道坐标、相机方向、短时擦边访问以及连续区域边界都有独立原生数据回归用例。

现有全量 STK 自适应计算中的 17 个格点出现访问次数或短时窗口差异。对这些格点，收集两边所有相关窗口，按卫星生成 554 段计算范围，再用原生 STK 的 0.002 s / 0.001 s 固定步长、`10⁻⁵ s` 事件容差重新计算。精化结果共 566 个窗口；两套步长以及独立 Python 结果均逐窗口核对，不能仅比较一个覆盖百分比。

特别保留了“同一次擦边经过形成两个窗口，中间有约 2 秒不可见间隙”的回归数据，防止把两个真实窗口连成一次访问。原生场景、实际采样参数、执行命令、窗口明细和输入哈希都随结果保存。

## 4. 单一入口与复现

在 `task2/` 目录使用项目环境安装 `requirements.txt`。当前依赖包括 numpy、pandas、scipy 和固定版本的 pyerfa；原生部分需要 Windows、STK 11.6 Engine 与可用的 Coverage 许可。

默认完整流程会重新运行 Python 和原生 STK，并写入新的时间戳目录：

```powershell
../../.venv-task2/Scripts/python.exe engineering_run.py --elements out/n28/constellation.csv
```

本次交付核对现有全量 STK 基线的输入与证据哈希，再重算 Python，并新跑原生擦边访问和 12 组太阳同步设计检查。对应命令为：

```powershell
../../.venv-task2/Scripts/python.exe engineering_run.py --reuse-stk out/stk_validation_eop2026 --out out/engineering_verified_20261110_final
```

输出目录必须新建或为空，因此重复执行时应换名，例如 `--out out/engineering_recheck`。复用只允许完全相同的物理输入：星座、历元、时段、边界、评价点、相机和 EOP 数据必须匹配；变更后应省略 `--reuse-stk`。历史运行的代码哈希保留为历史证据，当前运行另记录自己的代码哈希，不伪装成历史结果由新代码生成。

无复用的完整执行分支也已用单星七天场景实际跑通，两套原生全球和区域计算、窗口表导出、收敛与对齐检查全部通过，见 [入口实机回归记录](../out/engineering_entry_fresh_smoke_20261110/verification_summary.json)。该回归用于验证入口，不混入上面的 28 星指标。

冻结参数位于 [data/validation_profile.json](../data/validation_profile.json)。流程依次执行单元及数据回归测试、场景导出、两套 Python 全局搜索和区域步长、两套 STK 采样或合格的历史证据核验、轨道比较、擦边访问精化、逐窗口比较，以及多高度多轨道面太阳同步检查。任一检查失败则总状态失败；输入或代码在运行中改变也会拒绝通过。
